# Формат архивов shardkeep

Документ описывает, как устроена папка с архивами. По нему можно проверить и распаковать данные без shardkeep, стандартными программами `zstd`, `xz` и `tar`.

## Общая структура

```
OUT/
  README.md                                карточка датасета (необязательно)
  pack_shards.py                           скрипт восстановления (необязательно)
  verify_report.txt                        итог последней проверки
  data/<набор>/<набор>-00000.tar.zst       части набора
  data/<набор>/<набор>-00001.tar.zst
  manifest/<набор>/<набор>-00000.jsonl     манифест части
  manifest/<набор>/<набор>-00000.meta.json параметры части (формат 2)
  manifest/<набор>/plan.jsonl.gz           план упаковки
  manifest/<набор>/pack_settings.json      параметры набора
  manifest/<набор>/summary.json            сводка по набору
```

**Набор** – содержимое одной исходной папки. В одной папке с архивами может лежать несколько наборов.

**Часть** – архив tar, сжатый zstd (расширение `.tar.zst`) или xz (`.tar.xz`). В одну часть попадает примерно `shard_gb` гигабайт исходных данных (по умолчанию 4). Номер части записывается пятью цифрами, начиная с `00000`.

## Часть

- Формат tar: POSIX pax. Пути внутри архива относительные, с разделителем `/`, без начального `./`.
- В архиве только обычные файлы. Символические ссылки не упаковываются, пустые папки не сохраняются.
- У каждого файла сохраняется время изменения (с точностью до секунды), права доступа всегда `0644`, владелец не записывается.
- Сжатие zstd: в каждом кадре записана контрольная сумма. В режиме длинных совпадений окно равно 128 МБ (`window_log` 27), поэтому части распаковываются любой программой zstd без параметра `--long`. Многопоточная упаковка может записать файл из нескольких кадров zstd, и стандартные программы читают такие файлы как один поток.
- Файлы в плане отсортированы по папке первого уровня, затем по расширению, затем по пути. Похожие файлы оказываются рядом, и данные сжимаются лучше.

Распаковка без shardkeep:

```
zstd -d -c set1-00000.tar.zst | tar -x
```

## Манифест части (`<набор>-NNNNN.jsonl`)

Одна строка JSON на каждый файл части, кодировка UTF-8:

```json
{"path": "scenes/scene_001/sample.json", "size": 1532, "mtime": 1700000000, "sha256": "9f86d0..."}
```

| Поле | Значение |
|---|---|
| `path` | путь файла внутри архива и внутри исходной папки |
| `size` | размер в байтах |
| `mtime` | время изменения, целые секунды Unix |
| `sha256` | SHA-256 содержимого файла |

Манифест записывается последним, после файла части и файла параметров. Если манифест есть, значит часть записана полностью. Строки манифеста не меняются между версиями формата, и новые поля в них не добавляются.

## Параметры части (`<набор>-NNNNN.meta.json`, формат 2)

```json
{
 "format": 2,
 "tool": "shardkeep 0.1.0",
 "created": "2026-11-23T12:00:00",
 "file": "set1-00000.tar.zst",
 "codec": "zstd",
 "level": 19,
 "long": true,
 "window_log": 27,
 "threads": 8,
 "files": 1520,
 "raw_bytes": 4294000000,
 "compressed_bytes": 812000000,
 "sha256": "…",
 "skipped": [{"path": "logs/locked.txt", "error": "[Errno 13] Permission denied"}]
}
```

| Поле | Значение |
|---|---|
| `codec`, `level`, `long`, `window_log`, `threads` | с какими параметрами сжата именно эта часть |
| `files`, `raw_bytes` | число и общий размер файлов в части |
| `compressed_bytes`, `sha256` | размер и SHA-256 файла части. По ним проверка находит часть, замененную после упаковки, а сверка с хранилищем проверяет загрузку без скачивания |
| `skipped` | файлы из плана, которые не удалось прочитать. Их нет в архиве, и проверка считает это ошибкой |
| `jxl` | только при упаковке с `--jxl`: файлы JPEG, переведенные в JPEG XL, в виде `{"исходный путь": {"member": "исходный путь.jxl", "size": размер .jxl, "sha256": SHA-256 .jxl}}` |
| `jxl_fallback` | сколько JPEG оставлено как есть: перевод не удался, файл не восстановился побайтно или .jxl получился не меньше исходного |

## Файлы JPEG XL (`pack --jxl`)

При упаковке с `--jxl` файл JPEG переводится программой `cjxl --lossless_jpeg=1` и сразу восстанавливается обратно программой `djxl`. В архив попадает файл `.jxl` только тогда, когда восстановленный файл совпадает с исходным по SHA-256 и `.jxl` меньше исходного. Иначе в архив кладется исходный JPEG.

В архиве такой файл хранится под именем `<исходный путь>.jxl`. В манифесте записаны исходные путь, размер и SHA-256 файла JPEG, поэтому проверка с `--src` и распаковка по шаблону работают с исходными именами. Сопоставление имен лежит в поле `jxl` файла параметров части.

При распаковке shardkeep и скрипт восстановления `pack_shards.py` восстанавливают исходный JPEG программой `djxl` и проверяют его по манифесту. Без `djxl` параметр `--keep-jxl` извлекает файлы `.jxl` как есть. Вручную: `djxl файл.jpg.jxl файл.jpg`.

## План (`plan.jsonl.gz`)

Сжатый gzip список всех файлов набора в порядке упаковки: `{"s": номер части, "p": путь, "n": размер, "m": время изменения}`. В формате 2 у уже сжатых файлов (фото, видео, архивы) есть поле `"c": "low"`: такие файлы собираются в отдельные части и сжимаются низким уровнем. План создается один раз при первом запуске упаковки. При продолжении упаковки состав частей берется из него, поэтому файлы, появившиеся в исходной папке позже, в набор не попадают. Такие файлы находит проверка с параметром `--src`.

## Параметры набора (`pack_settings.json`)

```json
{
 "name": "set1", "source": "D:\\data\\set1", "codec": "zstd", "level": 19, "long": true,
 "shard_gb": 4.0, "created": "2026-11-23T12:00:00",
 "format": 2, "tool": "shardkeep 0.1.0", "profile": "auto", "level_low": 1, "window_log": 27,
 "excludes": ["*.tmp"], "include_env": false,
 "sessions": [{"started": "2026-11-24T09:00:00", "level": 22, "long": true, "tool": "shardkeep 0.1.0"}]
}
```

Поле `jxl` равно `true`, если набор упакован с `--jxl`. Поля первой строки есть в обоих форматах. `level` – уровень сжатия хорошо сжимаемых файлов при первом запуске, `level_low` – уровень для уже сжатых файлов (`null`, если уровень один для всех), `profile` – профиль сжатия. `excludes` и `include_env` – правила отбора файлов: по ним проверка с `--src` ищет в исходной папке файлы, которые не попали в архивы. `sessions` – продолжения упаковки и их параметры.

## Сводка (`summary.json`)

Пересчитывается после каждой упаковки:

| Поле | Значение |
|---|---|
| `name`, `codec`, `level` | имя набора, кодек и уровень при первом запуске |
| `shards`, `files`, `raw_bytes`, `compressed_bytes` | готовые части, файлы и объемы |
| `levels` | все уровни, с которыми сжаты части (формат 2) |
| `planned_shards`, `complete` | число частей по плану и признак завершенной упаковки (формат 2) |
| `skipped_files` | сколько файлов не удалось прочитать (формат 2) |
| `jxl_files`, `jxl_saved_bytes` | сколько JPEG переведено в JPEG XL и на сколько байт уменьшился объем до сжатия (только с `--jxl`) |

## Версии формата и совместимость

- **Формат 1** – архивы исходного скрипта `pack_shards.py`. В них нет файлов `.meta.json` и новых полей в `pack_settings.json` и `summary.json`.
- **Формат 2** – shardkeep 0.1 и новее. Добавлены файлы параметров частей и поля, отмеченные выше.

Правила, которые соблюдаются при изменении формата:

1. Новая версия shardkeep проверяет, распаковывает и продолжает упаковку наборов всех предыдущих форматов.
2. Структура папок, имена частей и строки манифестов не меняются. Новые сведения пишутся в отдельные файлы или в новые поля JSON.
3. Исходный `pack_shards.py` проверяет и распаковывает архивы формата 2: лишние файлы и поля он не читает. Исключение составляют наборы, упакованные с `--jxl`: исходный скрипт считает файлы `.jxl` лишними, а исходные JPEG отсутствующими. Для таких наборов нужен скрипт `pack_shards.py` из новой версии (он кладется рядом с архивами) или shardkeep.
